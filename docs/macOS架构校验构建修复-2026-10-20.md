# macOS 架构校验构建修复

## 问题现象与证据

[AstraGit Release 39352259174](https://github.com/skylight-f/AstraGit/actions/runs/39352259174) 对提交 `5ab5a44` 的验证与版本候选任务已通过，但 arm64、x64 两个打包任务都在创建 DMG 后失败。日志将失败定位到 `scripts/package-macos.mjs` 的原生更新辅助程序架构检查，错误包含：

```text
unknown architecture specification flag: ...AstraGitUpdateProgress
in specifying -verify_arch operation
```

该轮失败发生在打包校验阶段，不能由前面的源码门禁通过推断已经成功发行。

另核对[前次 Release 39196336304](https://github.com/skylight-f/AstraGit/actions/runs/39196336304) 的 arm64 日志，也包含同一 `lipo` 参数解析错误。云端诊断摘录保存在 `.tmp/acceptance/release-failure-diagnosis-20261020.json`。

## 根因

旧调用将参数排成 `lipo -verify_arch <架构> <文件路径>`。云端 Xcode 16.4 的 `lipo` 将末尾 `AstraGitUpdateProgress` 路径按待验证架构解析，因而拒绝该参数。修复将输入文件放在最前，使用 `lipo <文件路径> -verify_arch <架构>`，避免文件路径落入架构参数列表。

本机 `lipo` 对旧、新两种参数顺序都返回成功，没有在本机复现上述云端解析错误。根因证据来自失败工作流日志；本地测试用于验证修复后的真实架构校验及拒绝行为，不能替代修复提交的云端结果。

## 修复

- 新增 `scripts/macos-architecture.mjs`，集中调用 `/usr/bin/lipo`，按数组传递 `[filePath, '-verify_arch', target]`，不拼接 shell 字符串。仅接受应用架构 `arm64 / x64`，将 x64 映射到 Mach-O 的 `x86_64`，其他值直接拒绝。
- `scripts/package-macos.mjs` 使用该函数校验打包后的 `AstraGitUpdateProgress`，保留真实架构检查，不删除或忽略失败。
- Release 的 macOS 构建矩阵在正式打包前执行 `tests/macos-architecture.test.mjs`，让云端对应工具链先通过该原生回归。

## 验证结果与边界

- 原生专项 4/4 通过：本机用真实 `clang` 分别生成 arm64、x86_64 Mach-O 对象，验证匹配成功与错配失败；同时拒绝无效架构、普通文本文件和缺失文件，路径包含空格。
- 干净临时目录 `/private/tmp/astragit-release-repair-20261020-dqvzxxdo` 的 `pnpm install --frozen-lockfile`（417 项依赖复用缓存）、`pnpm setup:desktop` 及完整 `pnpm verify:publish` 均退出 0，109/109 测试通过。证据为该目录中的 `frozen-install.log`、`setup-desktop.log`、`verify-publish.log`。
- 同一干净目录的 `pnpm build:release` 已退出 0，生成 arm64 正式打包产物 `/private/tmp/astragit-release-repair-20261020-dqvzxxdo/release/AstraGit-0.1.11-arm64.dmg`，大小 119,830,617 字节。输入文件在前的原生辅助程序 `lipo` 校验通过，`codesign --verify --deep --strict` 与 `hdiutil verify` 校验通过，DMG checksum 为 VALID。
- `artifact-arm64.json` 与实际文件的 SHA-256、大小一致；应用 bundle ID 为 `com.astragit.desktop`，签名为 ad-hoc、未公证，ASAR 含 1,117 个条目。修复涉及的四个源码文件在当前工作区与干净构建目录的摘要一致。证据为 `.tmp/acceptance/release-build-repair-20261020.json` 和干净目录的 `build-release.log`。
- 本次是本机 arm64 打包验收；x64 仅通过真实 Mach-O 对象的原生回归，没有完成 x64 正式包构建。修复未推送，云端双架构工作流未验收，不能据此声称自动发布已经恢复。本任务未主动推送或发布。

## 经验总结

打包工具的参数顺序需要由目标平台实际执行验证。源码门禁、打包产物创建、打包后校验与公开发布是不同阶段；本地命令成功也不能替代对应提交在云端所用工具链上的结果。
