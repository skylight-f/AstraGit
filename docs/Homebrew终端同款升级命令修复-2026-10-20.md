# Homebrew 终端同款升级命令修复

## 问题与调整依据

用户已验证终端中的 `brew upgrade --cask skylight-f/tap/astragit` 可用，要求应用按同一命令执行。此前严格预取链路还显式执行 update、fetch、缓存检查，并将清单版本、URL、SHA 与 Cask 精确匹配，导致终端可以升级时应用仍可能被前置条件拦住。

本次以新的明确要求替代 10 月 19 日的严格预取策略。Main 中唯一控制器、后台调度、原生窗口与精确 App 重启继续复用；Direct 更新通道的下载、摘要、签名与安装逻辑不变。

## 当前执行路径

1. 公开发布信息用于发现高于当前运行版本的更新。确认当前 App 由指定 Homebrew Tap 与收据管理后，后台仅执行：

   ```sh
   brew upgrade --cask skylight-f/tap/astragit
   ```

2. brew 负责按用户已有环境刷新元数据、下载、校验与安装；应用不另外执行 `brew update / fetch / --cache`，不添加 `--no-quit / --yes / --require-sha` 等升级参数，不管理其下载子进程或自定义重连重试。
3. 升级进程环境保留 `HOMEBREW_NO_UPGRADE_QUIT_CASKS=1`，避免 Cask 的卸载退出步骤中断仍运行的 Main。该项是环境设置，命令参数保持上述形式；用户继承的 Homebrew 自动刷新偏好不被覆盖。
4. 升级后复验指定 Tap、实际目标 App、Bundle ID、App 两个版本字段和 Homebrew 安装收据。收据与 App 版本一致且高于当前运行版本即为 ready，不要求等于发布清单最新版本，也不要求 Cask 的下载 URL/SHA 与 Direct 产物逐项相等。Tap 尚慢一版但确实安装了更新，也可等待重启；brew 成功但没有升级到更高版本时不能标记 ready。
5. UI 明确显示 Homebrew「正在更新 → 更新已安装 → 重启生效」。用户确认重启后只复验实际已安装 App，不再执行第二次 upgrade；取消重启保留已安装事实。原生辅助程序继续等待旧 PID 退出后打开精确 App 路径与版本。
6. 同时到达的准备请求复用唯一进行中的升级；升级失败显示真实原因，不自动重试。用户显式重试才可再运行命令；重启复验失败不能回放升级。终端已经安装的新版可直接复验并等待重启，不重复 upgrade。

## 保留的范围约束

Homebrew 读取收据与 App 信息仍用于确认当前安装归属，不能接管其他 Tap 或其他路径的 App。开发应用不安装正式更新。临时 brew 替身仅在测试模式、系统临时路径允许；不更改正式安装、用户数据或 Direct 安装规则。

## 验证结果与边界

- `tests/homebrew-update.test.mjs` 12 项通过：临时可执行 brew 替身验证真实子进程参数、环境、一次升级与仅复验重启；覆盖过期元数据/不同清单产物不拦截、实际安装高于运行版本、Tap 滞后但可升级、no-op 不标 ready、并发合并、失败不自动重试、身份与版本不一致拒绝等。
- `tests/homebrew-controller.test.mjs` 12 项通过：隔离控制器验证已安装事实、取消与复验失败保持旧进程、后台单任务所有权、重启不重复 upgrade、失败只显式重试及 Direct 手动路径保留等。

## 经验总结

安装管理器的已验证命令应由管理器完成完整升级，避免应用另建清单对照、缓存或重试链路。界面需区分“已下载”和“已经安装、只待重启”，并以实际安装事实决定下一步。
