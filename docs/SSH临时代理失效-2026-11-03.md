# 推送时临时 SSH 代理失效

## 现象与复现

推送返回 `fatal: cannot exec '…/astragit-system-proxy-XXXXXX/ssh': No such file or directory` 和 `fatal: unable to fork`。Git 已启动，但无法启动这次连接所需的本机 SSH 包装脚本，不代表 SSH 密钥认证失败。已创建的本地提交不会因此撤销；不要重新创建同一提交。

在临时仓库中创建本地提交和裸仓库，模拟子进程继承旧的 `GIT_SSH` 后关闭旧代理环境，可稳定复现与截图相同的原生错误。

## 根因

Main 为系统代理创建临时 SSH 包装脚本，子进程继承其 `GIT_SSH`。退出清理会删除本进程脚本，但旧版初始化只判断 `GIT_SSH` 是否非空，无法区分用户显式 SSH 配置和应用上一进程留下的脚本。因此重启继承的旧脚本即使还在，也会使用旧的代理桥；旧进程退出后路径被清理，后续推送失败。

更新进度辅助程序和 DMG 安装器还会继承旧 Main 的整个环境，是需要隔离的长期子进程边界。截图能确认本机脚本缺失；不能仅凭日志断言具体是哪一种启动方式传入旧路径。

## 修复

- 为应用管理的代理桥和 SSH 脚本添加进程环境标记，新 Main 无论旧脚本是否尚存都创建自己的脚本。
- 兼容旧版无标记的 `GIT_SSH`：仅识别本用户临时目录中应用固定前缀、六位随机目录与 `ssh` 文件名的形状；兼容 macOS `/private/var` 与 `/var` 别名。
- 更新辅助程序、DMG 安装器与重新启动的应用使用剥离当前 Main 临时代理的独立环境；保留其他变量及用户显式 SSH 配置。清理仅删除本进程创建的目录，子进程退出不恢复已过期的父进程脚本。
- 缺失应用 SSH 脚本时返回专门错误码和中英文提示，建议完全退出后重新打开并核对远端状态；不自动重复推送，也不擅自绕过系统代理直连。

## 验证

回归覆盖删除旧脚本后的真实 Git push、旧脚本尚存时的新桥隔离、更新子进程环境清理、用户 SSH 配置优先级与缺失脚本错误说明。76 项针对性检查通过；全新临时目录 frozen-lockfile 安装与完整 `pnpm verify:publish` 通过，612 项通过、0 失败、0 跳过，包含既有 Git LFS 3.8.0 原生检查。

真实 Electron 进程探针通过 `createNativeUpdateProgressHost` 的实际 spawn 验证辅助程序没有继承应用临时 SSH 和代理变量，正常关闭且进程退出 0。

复用干净源码副本运行独立 `pnpm dev`，端口临时改为 5189，仅此开发配置与工作树不同；数据和应用身份独立，未停止既有 5179 开发会话。刻意传入已删除的旧版 `GIT_SSH`，冷启动及 Main 热重启（PID 78857 → 87779）后均恢复测试项目，真实界面抓取能启动 `/usr/bin/ssh` 与 `nc`，不再报告脚本缺失。测试远程固定为本机端口 1，连接失败是预期边界，不作为外部 Git 服务器连接成功的证明；真实 push 的成功证明来自前述本地裸仓库 receive-pack 集成测试。
