# Git 提示与冲突反馈优化

## 问题现象

Git 原始诊断在 core、服务或 HTTP 错误包装中丢失，界面可能只显示通用失败信息；切换被本地更改保护性阻止、操作前已有冲突、整合产生冲突和恢复本地修改产生冲突未得到清晰区分。表单失败后重新初始化、日志直接占满弹窗，以及操作完成后刷新失败被误认为动作失败，也会妨碍用户判断下一步。

## 根因与修复

### 1. 从 Git 命令边界保留诊断与执行事实

- `packages/git-core/src/index.ts` 在真实 Git 子进程边界分类固定诊断，保留脱敏后的命令、标准输出、标准错误、退出码及执行阶段，不再由 `runGit` 重包成只有通用消息的错误。子进程使用 `LANG=C / LC_ALL=C` 获取稳定的 Git 诊断，不根据任意界面正文或文件名猜测错误类别。
- 分类覆盖提交身份、空提交、索引锁、已有冲突、未结束整合、本地更改保护、远端身份验证、网络、非快进与服务器拒绝、签名、Hook 和执行程序异常。保护性拒绝确认未写入时标为 `failed_before_write`；超时、已执行写操作或尚无法核对的结果保留 `unknown_after_write`。
- 分支切换区分已跟踪修改和未跟踪文件覆盖，保留 `blockedBy`，已有冲突则在执行切换前直接拒绝；不会自动贮藏或强制覆盖。
- 合并、变基、拉取和应用贮藏返回已留下的冲突状态，而不是抹成普通命令失败。Smart Update 区分整合阶段与恢复阶段，只有核实仍保留的临时贮藏才返回 `savedStash`。
- 所选文件提交创建索引锁失败时，明确返回锁占用及写入前拒绝状态，不自动删除锁文件。

### 2. 服务与 HTTP 不丢失错误身份

`projectGitWorkbenchService.ts`、服务错误响应及 `localApiTransport.ts` 保留错误码、详情、`blockedBy`、执行阶段和执行状态。操作记录保留真实 Git 诊断；Git 动作已有明确结果但后续快照读取失败时，返回独立刷新错误并保留已确认的完成或冲突事实，不覆盖操作历史中的完成记录。

本机 API 的读取超时与写入请求超时分开：GET/HEAD 是读取超时，写入请求超时提示结果尚未确认，不能据此重复提交或推送。

### 3. 两个视图使用一致的下一步提示

| 场景 | 界面说明与下一步 |
| --- | --- |
| 切换会覆盖已跟踪修改 | 明确切换未执行，先提交或贮藏，再重试；提供正确仓库的贮藏入口 |
| 切换会覆盖未跟踪文件 | 提醒备份并移开，或贮藏时包含未跟踪文件，避免推荐默认不包含它们的普通贮藏 |
| 切换前已有冲突 | 明确冲突早已存在、切换未执行，进入该仓库文件状态处理 |
| merge/rebase/pull 产生冲突 | 指出整合暂停，选择正确仓库和冲突文件；解决并暂存后继续或终止已有整合 |
| 应用贮藏产生冲突 | 明确贮藏仍保留，先解决并暂存，不重复应用 |
| Smart Update 恢复本地修改时冲突 | 明确更新步骤已执行，冲突出现在恢复阶段；仅显示实际保留的贮藏标识 |
| Smart Update 整合冲突且保留自动贮藏 | 明确先前本地修改尚未恢复，完成或终止整合后再检查并恢复该贮藏，与恢复阶段的“不要重复应用”区分 |
| 动作结果已确认、刷新失败 | 保留已完成或已产生冲突的事实，先刷新核对，不重复动作 |
| 写入请求超时、结果未知 | 明确尚不能确认结果，先核对仓库与远端状态，不由内层错误推断未执行 |

- `gitOperationFeedback.ts` 统一动作、仓库、目标分支和冲突阶段提示；`userFacingError.ts` 提供中英文解释，优先保留结果未知、刷新与恢复事实。
- 仓库管理的错误首屏呈现原因和下一步；真实诊断留在默认折叠的「Git 日志」中。已有冲突指向正确仓库的文件状态，不把历史查看选中仓库当成执行目标。
- 项目级冲突横幅显示项目冲突总数和实际冲突仓库名称；点击处理冲突时选择存在冲突的仓库与文件，避免当前选中仓库没有冲突时误导用户。
- 新分支、指定提交、贮藏和推送等表单仅在确认完成时关闭；失败保留输入及推送目标。执行期间禁止变更操作范围；项目更新产生冲突后禁止再次整批更新，提供处理冲突入口。
- 项目提交视图的批次、预览、差异和重试错误保留错误码及诊断，再由统一组件翻译；不会仅存一段失去错误身份的 `Error.message`。失败推送继续保留已有提交和原目标，重试沿用原提交。
- 将错误链中每一层的错误身份放在长日志前，避免日志截断后丢失真实分类；外层已核实的恢复或刷新事实优先于内层通用命令错误。项目提交在分支或 HEAD 变化后清除该仓库旧勾选，执行新动作时清除过期反馈。

### 4. 诊断可用但不暴露凭据

core 和公共错误格式化对 HTTP/SSH URL 凭据、Basic/Bearer、GitHub/GitLab token、私钥及常见密钥字段脱敏；公共可见诊断也隐藏用户绝对本地路径。命令、相对文件路径和服务器拒绝原因继续保留，不以删掉整份日志代替脱敏。

## 经验总结

Git 错误提示必须由执行边界的明确分类和核实后的状态驱动；外层流程掌握的恢复、刷新和结果未知事实不能被内层诊断覆盖。错误正文用于解释原因，原始日志用于排查，两者应分别呈现并共同脱敏。
